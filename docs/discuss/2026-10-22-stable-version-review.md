# 当前稳定版本的代码审阅与优化建议

日期：2026-10-22。范围：当前分支 `feat/61021`、提交 `1069830`，正式构建链、固定参考驱动、安装/卸载、测试及发行材料。本文件是审阅建议，不是新的实施 PRD；本轮不修改实现、不重新安装或重载音频服务。

## 原始需求与已知基线

用户反馈：手动安装后经过一天多测试，当前版本已比较稳定，希望分析整个项目代码，先给出优化建议。此前“原样复现再部署”的阶段已形成用户实际使用基线，后续改动应以保护该基线为前提。

只读检查已装 `TapSayAudio.driver`：Bundle ID `com.leafney.tapsay.audio.driver`，版本 `0.1.0`、构建 `1`，可执行文件 SHA-256 `df3926398fce9633c21c1a202e79272f514a8076bae84b19c31d8f06452e1633`，与上次最终交付相同。对应构建源码提交 `f9f962b0e0bb55b89181960f7944d68ab18eeaf6`。用户的稳定反馈已记录；具体软件版本、测试次数和全部支持格式的实际覆盖尚未独立取得，不能据此推断所有软件及属性分支都已验收。

本轮没有新增需求问答。结论来自仓库审阅、已有隔离测试证据和三项新增隔离复核。

## 审阅结论

当前最有价值的优化是减少维护歧义、完善版本与构包可靠性、修正安装卸载的边界结果。默认 48 kHz、双声道、参考采样率表、隐藏设备、缓冲和 IO 算法宜继续保持。没有取得 CPU、内存、丢帧或延迟测量证据支持音频算法重写。

### 1. 驱动属性层有已知缺陷，安排独立修复批次

位置均指向实际参与构建的固定上游源码 `third_party/blackhole/upstream/BlackHole/BlackHole.c`；当前正式链为 `prepare-driver-source.py` → 无线麦 USB 补丁 → TapSay 身份补丁。旧 `Driver/` 不属于当前正式源码。

| 位置 | 发现 | 建议及验收 |

| `BlackHole.c:2698`，计数函数 `:559` | 主控制列表计数包含关闭的 Pitch，复制却跳过；读取循环没有数组上限。已有隔离 AddressSanitizer 证据复现越界；列表也未始终按请求 scope 筛选 | 使计数/筛选一致，循环限制数组与容量，在同一状态快照读取；验证主/隐藏设备、各 scope、Pitch 状态和容量边界 |

这些是属性查询的正确性和兼容性问题，不是已证实的日常音频故障原因，也不是性能优化。用户当前稳定的使用路径可能没有覆盖相关查询分支。建议放在外围工程修整之后，采用小补丁、单独提交、隔离测试和同条件真机对照；不与重采样、时钟、缓冲或 IO 改动合并。

当前 `check-reference-source.py` 明确禁止身份之外的 C 差异。若批准修复，需先调整审计规则：保留原样参考对照，再逐项审阅明确的修复补丁，不能为了让构建通过而关闭对照。`proposals/control-list-safety.patch` 是历史候选，不能直接作为已覆盖全部问题的补丁使用。

### 2. 卸载结果生成与解码合同不一致，建议优先修正

位置：`Tools/Transaction/UninstallResult.swift:54` 与 `:127`，界面消费点 `Tools/Transaction/Uninstaller.swift:82`。

当声卡、收据和状态已删除、设备也消失，但历史材料清理为 partial 或 blocked 时，`outcome` 生成 `status=removed` 和具体保留路径；同一文件的 `decode` 却要求 removed 只能配 complete/notNeeded、且无剩余路径。这使界面进入“无法确认卸载结果”，丢失原本可以显示的准确结果。

本轮只在独立进程构造结果并编码/解码，未执行真实卸载：partial 和 blocked 两种组合均被拒绝，错误代码 5。现有 `Tests/UninstallResultTests.swift:72` 检查了对象标题和消息，未对这个分支执行编码再解码，因此已有测试能通过而漏掉问题。

建议统一一份结果状态矩阵，保留“设备已卸载、部分历史材料保留”的真实语义，并给每个合法结果增加完整往返校验。该改动不触及驱动音频路径。

### 3. 发行检查发现错误仍可返回成功

位置：`scripts/check-release-readiness.py:54` 与 `:136`。

脚本会收集散列不一致、DMG 校验失败、源码缺文件等问题，但普通模式仅根据资产是否缺失返回失败；文件存在时，内容检查已经失败仍可能退出 0。`--formal` 虽会失败，但同时包含尚未完成的签名/发布门槛，无法区分包本身错误和本地测试包尚未正式发布。

本轮将实际资产复制到临时目录，改动校验文件的一个字符，替换外部签名/DMG命令为成功桩，仅验证脚本判定逻辑：输出已包含“不一致”，返回值仍为 0。

建议分开两类结果：内容、散列、架构等硬错误在所有模式失败；签名、公证、真实下载与验收状态由正式发布模式额外检查。不要将不支持的 Intel 当成本轮 arm64 正式发布的永久未满足项。

### 4. 下一版本的版本信息尚未贯通

位置：`scripts/check-metadata.py:33`、`third_party/blackhole/tapsay-identity.patch:147`、`Uninstaller.app/Contents/Info.plist:9`、`scripts/check-uninstaller.py:31`。

元数据检查将 version/build_number 固定为 0.1.0/1。身份补丁又将驱动 CFBundleVersion 写为字面量 1，而构建脚本传入的 CURRENT_PROJECT_VERSION 没有被该 plist 字段引用。卸载 App plist 及内置 product.json 也分别维护。修改唯一配置并不足以正常发布下一版本。

本轮用临时配置尝试 0.1.1/2，元数据检查立即拒绝，未更改仓库配置。

建议 `config/product.json` 成为唯一版本来源，构建时生成派生 plist/内置配置和说明中的版本名；稳定 UID、Bundle ID、工厂 UUID继续固定。验证不同版本、构建号的一致性，并保留原有同版重装及升降级行为。

### 5. 构包失败会提前清掉已有产物

位置：`scripts/build-packages.sh:25`。

脚本在元数据验证和新构建之前，删除同版本 PKG、DMG、源码包及 SHA256SUMS。若后续构建失败，之前可用的包已经消失；失败过程中 dist 还可能存在不完整的一组新旧结果。

建议完整构包和检查都放到独立暂存目录，通过后统一替换正式输出；失败只清理本次暂存。当前“准确读取本次驱动构建结果并比对散列”的做法应保留。收益是构包可恢复，不需要修改声卡本身。

### 6. 收敛旧代码、旧测试入口与文档

仓库仍同时保留旧 `Driver/`、`config/driver-profiles.json`、实验构包/生成脚本和多轮过期计划。`scripts/run-driver-contract-tests.sh:9` 默认 legacy，使用旧 `Driver/TapSayAudioTests/main.c`；其通过不能证明当前固定参考驱动通过。`check-package.py` 仍支持旧 profile 参数并将当前包打印为 legacy，增加理解成本。

建议正式构建、正式合同测试各保留唯一入口，测试从本次构建结果获得源码与产物；先检查引用，再清理已无消费者的旧文件。历史决策可由 Git 追溯。保留固定上游、许可证、当前产品规格、用户实测与必要故障摘要；不删除系统驱动或本机恢复证据。

`scripts/test-native-transaction.py:17` 使用 `.build/latest-driver.json`，而构包使用每次独立的结果文件；两者应显式指向同一次构建，避免检查的对象与交付对象不同。源码归档还收录了 `Tests/DriverContract.c` 却未收录对应 HAL 测试运行脚本，测试交付应一并收敛。

### 7. 改善诊断与安装结果，控制改动范围

位置：`Tools/Transaction/main.swift:221`。安装状态长期保留 verification_status/audio_chain_status=not_run，激活仅记录 pending_verification/restart_required；文件部署成功后没有自动读回结果。DMG 说明写“安装完成后重新枚举声卡”，实现与表述不够一致。

建议提供可单独运行的只读诊断报告：本产品 UID、实际名义率、输入输出物理/虚拟格式、磁盘驱动版本与散列、系统版本、验证时间。分别报告“文件已部署”“设备已枚举”“合成 PCM 通过”“真实遥控器通过”。磁盘文件散列不能单独证明 CoreAudio 已加载同一个运行实例；无法证明时如实标记。

先改善信息与用户提示；不在这次建议中引入自动改格式、自动修复、额外重试或频繁重启音频服务。手动部署仍由用户执行。

## 推荐实施顺序

1. 固化当前基线：稳定源码/包/驱动散列，记录用户一天多稳定实测及对应系统/软件条件。给后续每次变化提供可回退的对照。
2. 第一批只处理外围：旧入口与文档整理、版本贯通、检查退出码、构包暂存发布、卸载结果合同。以实际驱动文件散列未改变作为尽量保持当前驱动不变的验收依据。
3. 第二批逐项处理驱动属性缺陷：每项独立补丁和回归；先比较合同回调，再测真实软件与遥控器切回，失败即回退该项。完整修复仍保持默认 48 kHz、格式表、对象布局和 IO 主路径。
4. 后续正式发行准备：有发行账号后完成签名、公证和真实下载核验。这属于发行条件，不与驱动功能优化混为一项。

暂不建议修改默认采样率、删减参考率表、删除隐藏设备、改变缓冲/时钟或重写混音/恢复逻辑。支持较高采样率的常量列表不表示设备平时就在那些采样率运行；删表不会自然带来当前 48 kHz 链路的性能提升。更深入的音频性能优化应先有 CPU、延迟、丢帧或多客户端场景的测量依据。

## 验证边界

已做静态审阅、已装二进制只读核对、卸载协议独立 Swift 复核、版本临时配置复核、发行检查临时目录故障注入。临时编译与结果位于 `.build/review-2026-10-22/`，未修改产品实现；没有重新安装、卸载、切换采样率或重启音频服务。此前驱动属性缺陷的隔离证据继续引用既有记录，本轮未向运行中的音频服务执行相关失败查询。
