# 虚拟声卡参考配置基线讨论

日期：2026-10-20
状态：PRD 已批准，按阶段实施中。

## 原始需求与问题

用户在同一个 TapSay 主程序中，从无线麦的 MiRemoteV 2ch 切回 TapSay Audio 2ch，
偶发遇到“虚拟声卡播放就绪验证超时，本次语音结束”，无法正常识别遥控器语音。
反复修改初始化与恢复流程后，仍未确定根因。

用户提出：先将 TapSay Audio 的功能配置按无线麦驱动一比一对齐；
基线验证正常后，再单独将默认 48 kHz 改为 16 kHz，逐项验证优化。
本轮不继续叠加主程序恢复补丁。

## 问答与已明确的要求

1. 用户问：两个驱动都基于相同开源项目，为何表现不同？
   - 当前调查结论：配置和对象枚举确有差异；共同上游不能证明最终行为相同。
     现有证据不能证明采样率就是根因，也不能证明本机安装的无线麦二进制与本地源码完全对应。
   - 用户决定：停止沿原路径反复修补，建立参考配置基线，再测试。
2. 用户问：在当前项目修改，还是切换到虚拟声卡项目？
   - 助手答：驱动代码、配置、文档和提交归入 tapsay-audio；tapsay 固定为测试客户端。
     当前会话已能访问两个目录，无须重新开会话。
   - 用户答：“很好，那就在当前会话中更改虚拟声卡项目，继续给出相关优化 PRD 文档。”
3. 是否只改默认采样率即可？此问题通过代码核对回答，未再次要求用户回答。
   - 结论：不够。必须核对完整采样率表、隐藏设备、设备与 Box 的 transport、
     时钟、缓冲区、控制属性和实际构建参数。
4. 是否复制参考项目的产品身份？此项为待 PRD 整体审批的实现建议。
   - 建议：保留 TapSay 独立名称、UID、Bundle ID、工厂 UUID、包身份及许可材料，
     防止覆盖或混淆 MiRemoteV。功能等价不表示二进制字节一致。
5. 是否复制已知对象返回错误？此项为待 PRD 整体审批的实现建议。
   - 建议：保留 OwnedObjects 返回数组的安全修复，单独列为最小差异。
     不把有明确返回数据错误的实现重新引入系统进程。
6. 是否现在安装或改生产代码？
   - 最新用户请求是继续给出 PRD；本轮只生成文档，待批准后实施。
7. 用户补充：PRD 将交给低智能模型编码，要求进一步补充细节，避免误解。
   - 处理：增加逐文件职责、profile 数据合同、与上游逐项比对方法、分阶段命令和门槛、
     自动测试案例、系统操作权限边界、失败停止条件及提交内容模板。

## 本地证据

- 参考项目：`../apps/remote-mic-app`，提交
  `c9fabd1ef53e1a311dab4518a70693494631368b`。
- 参考脚本：`scripts/build-doubao-driver.sh`、
  `scripts/release-variant.sh`。
- 参考补丁：`third_party/blackhole/blackhole-device-usb.patch`。
- 两个项目均指向 BlackHole v0.7.1，提交
  `e2b22aaaba4e507a097131704bf96dabc004d9cf`。
- 本地固定版本源码副本中，初始采样率为 48000；
  支持 13 种采样率；Device 的 transport 是 Virtual，Box 也是 Virtual。
  无线麦补丁只把 Device 改为 USB，没有把 Box 改为 USB。
- 无线麦构建只覆盖驱动名、Bundle ID、双声道等参数，没有缩减采样率表。
- 当前 TapSay 配置默认 16000，仅支持 16000/44100/48000；
  收缩了插件及 Box 的设备枚举，并把 Box 的 transport 也改为 USB。
- 上游插件 OwnedObjects 两次写入索引 0，当前派生代码已修正第二次写入索引 1。
- 本地临时源码仅用于调查；实施时必须重新核验来源，不能将临时目录作为构建依赖。

## 最终共同方向与审批边界

已明确方向：在独立驱动项目建立无线麦参考配置基线，固定主程序，先测 48 kHz，
再考虑单独测试 16 kHz。profile 接口、测试次数、逐文件改动边界及实施门槛已在
配套 PRD 中写成可执行提案，仍需用户批准后实施。

主程序仓库 2026-10-20 的 audio-switch-readiness-recovery 草案暂缓，
故障日志仍作为后续失败对照证据。基线通过不能直接证明唯一根因；
基线失败也不能自动转为修改主程序超时策略。
