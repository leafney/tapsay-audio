# 无线麦参考配置基线与采样率对照 PRD

日期：2026-10-20
状态：用户已批准，按阶段实施中。
所属项目：tapsay-audio。

## 1. 问题陈述

同一个 TapSay 主程序在 MiRemoteV 2ch 和 TapSay Audio 2ch 之间切换时，
后者偶发播放就绪验证超时。已有自动矩阵使用模拟输入服务并关闭自动声卡配置，
未覆盖用户实际路由切换，因此不能用既往通过结果否定用户反馈。

两个驱动来自相同上游，但功能配置存在差异。当前无法证明默认 16 kHz、
隐藏设备收缩或其他差异中的哪一项导致故障。继续同时修改主程序和驱动会使结果难以解释。

## 2. 方案与成功定义

建立可复现的无线麦参考功能基线，先用 48 kHz 验证。
通过后再建立只改变初始默认采样率的 16 kHz 对照配置。
同一实验期间固定 TapSay 主程序、测试流程和第三方输入工具。

“一比一”在本 PRD 中指：音频配置及正常运行路径对齐参考源码与构建设置。
保留自有身份、许可材料及明确的数据返回安全修复，并完整列出差异。
不宣称与无线麦安装二进制逐字节相同。

成功必须包括真实路由切换、真实 RC003 长按说话及运行一段时间后的复测。
设备名称可见、静态属性正常、探测通过和实际语音可用分别记录，不能相互替代。
即使整批通过，也只说明该环境与样本内未复现，不宣称永久无故障。

## 3. 用户故事

1. 作为用户，我希望先得到配置与无线麦一致的驱动，减少同时排查的变量。
2. 作为用户，我希望已有 MiRemoteV 驱动保留，以便随时做对照。
3. 作为用户，我希望设备仍显示 TapSay Audio 2ch，避免选错设备。
4. 作为测试者，我希望知道当前加载的具体构建，避免测到旧驱动。
5. 作为测试者，我希望知道实际采样率，避免把初始默认值当成运行值。
6. 作为遥控器用户，我希望切换声卡后仍能长按开始、松手结束。
7. 作为用户，我希望运行一段时间后仍可稳定使用。
8. 作为用户，我希望失败时能够恢复安装前驱动与音频选择。
9. 作为维护者，我希望每个测试结果都能追溯到源码、配置和安装产物。
10. 作为维护者，我希望默认 16 kHz 的影响能够单独验证。
11. 作为维护者，我希望失败日志包含成功与失败样本，而不只是最终报错。
12. 作为发行维护者，我希望实验包与正式发布材料明确区分。

## 4. 范围与规格优先级

本 PRD 批准后，仅对本轮实验覆盖旧发行 PRD 中“默认 16 kHz、
仅三种采样率、不公布隐藏设备、Box transport 为 USB”的相关约束。
安装事务、卸载范围、稳定设备身份、不开启自动重启和不自动修改默认输出等规则继续有效。
实验结果不自动等于新的正式发行合同。

主程序的 audio-switch-readiness-recovery 草案暂缓，不在本轮实施。
不调整主程序音频图、就绪判定、探测回调、超时预算或缓存上限。
测试暴露出的其他问题独立记录，避免混进当前对照。

## 6. 功能配置合同

### 6.1 两种实验配置

| 配置 | 初始默认采样率 | 用途 |
| --- | --- | --- |
| reference-48k | 48000 Hz | 首先实施、安装和验收的参考基线 |
| reference-16k | 16000 Hz | 48 kHz 基线通过后，单独验证初始默认率变化 |

两者除初始默认率及实验追踪字段外，源码、宏、采样率列表、对象布局、
构建工具和参数必须相同。保留原版本的 Git 提交与回退产物，不把旧三采样率配置冒充新 16 kHz 对照。

### 6.2 必须对齐的项目

| 项目 | 参考基线要求 |
| --- | --- |
| 声道 | 双声道，主设备输入和输出均启用 |
| 采样率列表 | 8000、16000、24000、44100、48000、88200、96000、176400、192000、352800、384000、705600、768000 Hz，顺序保持上游 |
| 主设备隐藏属性 | false |
| 第二设备 | 恢复上游隐藏第二设备对象、名称规则、输入输出及 UID 翻译行为；隐藏属性为 true |
| 枚举 | 插件与 Box 的 DeviceList、长度和 UID 查询按参考语义恢复；不是只修改隐藏宏 |
| Device transport | USB，沿用无线麦补丁 |
| Box transport | Virtual，沿用上游；撤销当前额外 USB 修改 |
| 延迟与缓冲 | latency 0，Device RingBufferSize 16384，ring buffer 65536 帧 |
| 时钟与时间戳 | 保留参考主机时钟换算、采样率切换及零时间戳逻辑 |
| 音量、静音、默认设备资格 | 对照参考有效宏和属性处理逐项一致，不趁机收缩 |
| 音频流格式与 IO | 使用参考格式宣告及读写逻辑，不新增转采样或缓冲策略 |
| 正常状态通知 | 对照上游采样率、启动停止及对象属性变更路径，无额外恢复补丁 |

隐藏第二设备仅属于驱动对象兼容实验。主程序和引导页仍只展示受支持的主设备；
不得向用户展示两个可选的 TapSay 语音声卡，也不得复制 MiRemoteV UID。

### 6.3 必须保留并公开的最小差异

| 差异 | 处理要求 |
| --- | --- |
| 产品身份 | 保留 TapSay 主设备名称、Bundle ID、主设备/Box/Model UID、工厂 UUID、安装包及卸载身份 |
| 第二设备身份 | 增加独立且稳定的 TapSay 第二设备 UID，不改变主设备 UID，不与其他标识冲突 |
| 制造商与品牌 | 保持 TapSay，移除未经采用的品牌图标及伪硬件序列号 |
| OwnedObjects 安全修复 | 保留第二项写入索引 1 的修复；返回长度、容量检查及实际写入必须一致 |
| 许可与来源 | 保留原版权、许可证、修改记录和可重建材料 |
| 平台合同 | 两个架构仍保持本项目 macOS 14 起支持；参考 Intel 的 macOS 13 下限仅记录，不扩大支持范围 |

上述差异属于实验限制，不能写成已证明与故障无关。
若认为必须进一步排除某项差异，先形成追加方案，禁止暗中恢复已知错误或覆盖其他驱动身份。

## 7. 实施决策

### 7.1 配置与构建

建立一个实验配置选择入口，构建、配置生成、元数据检查、驱动契约检查和打包全部使用同一选择结果。
建议统一参数为 `--profile reference-48k` 或 `--profile reference-16k`。
未知配置、参数缺失或元数据不一致须在写入产物前失败，不能静默回落至旧配置。
现有正式发行入口保留原合同；实验必须显式选择配置。

生成文件和中间产物按配置及架构隔离，不在两个实验之间复用旧头文件或已编译对象。
若现有工具必须写源码旁生成文件，则构建串行进行，先清晰验证生成内容，
并在结束时恢复原生成文件；不得依赖并行修改共享生成文件实现隔离。

产物清单必须包含：配置名、源码提交和是否有未提交改动、上游提交、
参考补丁散列、完整有效构建设置、Xcode/SDK、架构、部署下限、签名方式、
初始率及支持率表、允许差异清单、驱动与包散列。
驱动包内需带同一实验清单，便于核对磁盘安装内容；清单不替代确认运行中的加载状态。

先比较参考与本项目 Release 的实际 build settings，再对齐会影响驱动代码生成和链接的参数。
参考使用 ONLY_ACTIVE_ARCH=NO、按发行架构构建；产物保留同样的 strip 与本地签名步骤。
自有项目/目标名、版本和产物目录允许不同。
不能只改命令行中的一个参数便宣称构建等价。
两个架构均需构建与静态检查；非本机架构只能标注“构建通过，真机未验收”。

### 7.2 安装与实验辨认

实验仍安装为原 TapSay 驱动身份，替换其一个安装实例；不增加第三种可见声卡。
包文件名及清单区分配置与构建编号。不能只看设备名称或产品版本区分实验。
复用现有覆盖安装、失败恢复及卸载事务，不为实验新增另一套系统安装逻辑。

替换前记录已装 TapSay 驱动备份及散列，并保留可用的回退入口。
不得改动 MiRemoteV 安装目录、身份、收据及卸载材料。
不得自动把 TapSay 设为系统默认输出或提示音输出。
测试确需更改系统输入或采样率时，记录原值、范围与恢复操作，再经用户授权执行。
需要停止主程序、重启音频服务或重启系统时，同样先说明并获得对应授权。

磁盘上包替换成功不等于音频服务已加载新驱动。需按现有安装结果及必要的授权重启流程确认；
无法确认时将该轮标记为“加载版本未确认”，不能计入验收。

### 7.3 初始默认值与实际采样率

驱动全局变量初始值不等于设备最终运行率。CoreAudio、已有客户程序及历史设置可能再次请求改率。
每次安装后以及每次切换、探测前后，都记录名义采样率、实际流格式、
输入输出声道和当前设备 UID。

区分两类结果：

1. 初始默认率：契约检查验证驱动初始值；真实首次加载若能采集也记录。
2. 指定运行率：经授权设置并读取确认 48 kHz 或 16 kHz 后，测试该运行条件。

若固定主程序自动把设备改为 16 kHz，不修改主程序绕过：
如实记录 reference-48k 在真实应用下实际运行 16 kHz。
这可以验证参考配置兼容性，但不能写成“真实 48 kHz 运行验收通过”。
需要单独 48 kHz 回环测试时用独立诊断工具，并与主程序真实场景分开报告。
同理，reference-16k 实际仍运行 48 kHz 时不能宣称完成 16 kHz 实测。

## 8. 测试决策

### 8.1 自动检查

复用已有驱动契约测试，按配置传入预期，避免把旧 16000 和三采样率断言直接删除。
重点检查边界行为，不为每一个生成常量添加重复测试。

- 元数据：未知配置拒绝、身份冲突拒绝、两配置之间仅允许预期字段变化。
- 对象合同：主/隐藏设备可按约定枚举和 UID 查询；长度查询和数据返回一致。
- 数组边界：OwnedObjects、DeviceList 的零容量、部分容量、足够容量及未获取 Box 状态；
  确保无越界写入、未初始化返回项和虚报长度。
- 音频属性：初始率、完整支持率表、非法率拒绝、transport、双声道和隐藏属性。
- 构建产物：架构、最低系统、插件工厂登记、依赖和签名有效；清单匹配实际配置。
- 安装事务：已有安装/回退检查继续通过，不能因实验配置削弱路径安全约束。

自动检查通过后才能安排实机安装；不采用 TDD，不重写整套现有测试。

### 8.2 真实环境与记录

固定 Mac、系统版本、RC003 遥控器、TapSay 可执行文件、第三方输入法版本和快捷键配置。
使用已具备有效录音权限的终端或诊断宿主。
无权限宿主录得全零时先标记权限条件不满足，不能直接归因驱动。
真实路由组必须使用实际设备选择服务，不能使用模拟输入服务替代。

每轮记录统一批次号、操作时间、设备 UID/动态 ID、运行率、应用就绪状态、
播放探测结果与耗时、失败码、按下/释放事件、音频样本是否实际到达。
保存相关运行日志起止区间，区分取消、初始化等待、探测失败及识别工具未输出文本。
不新增主程序恢复逻辑；现有日志不足时允许使用独立只读诊断工具采样。
记录内容默认不保存用户语音或识别文本；必要信号测试使用明确的测试信号。

### 8.3 reference-48k 验收矩阵

先为现有 MiRemoteV 记录同条件对照，再对参考基线执行以下矩阵：

| 场景 | 最低样本 | 通过条件 |
| --- | --- | --- |
| 冷启动 | 10 轮 | 实际加载身份已确认，初始化最终成功，等待就绪后真实语音可用 |
| MiRemoteV 切回 TapSay | 20 轮 | 每轮确认实际输入路由及运行率；就绪后真实长按说话成功，无播放验证超时 |
| 运行后复测 | 应用连续运行至少 60 分钟；每 15 分钟 5 次长按，共至少 20 次；末尾另做 10 轮切回 | 无用户报告的持续退化或连续失败，日志与操作可对照 |
| 按键边界 | 初始化中按下、快速松手、连续长按各 5 次 | 按既有合同等待或取消，不遗漏释放、不遗留第三方触发键按下状态 |
| 独立音频回环 | 主设备 16/44.1/48 kHz 每率 5 轮 | 有效宿主录回非零测试信号，格式正确，无持续丢失 |
| 第三方工具实际使用 | 每个本轮声明支持的工具至少 5 次 | 用户确认可输入文字；失败须区分音频路径和工具自身配置 |

MiRemoteV 对照至少覆盖同样的 20 次切回、60 分钟运行观察和长按样本；
固定先后顺序，尽量保持相同系统条件。任一实际失败保留，不用重试成功覆盖。
其余场景尽可能同条件对照，并列明未做项。

虚拟声卡验收加入人工识别确认不改变主程序引导页产品合同：
程序依然不自动判定第三方识别文字是否正确。

若本机 MiRemoteV 同样失败，标记环境或共同链路问题，先复核，不判定本驱动合格。
reference-48k 出现任何目标超时或音频链路失败时，停止进入下一阶段，保留失败现场并给出下一步分析。

### 8.4 reference-16k 门槛

只有参考基线自动检查与适用实机矩阵完成，且无未解释目标故障，才进入此阶段。
仅改初始默认率，重新构建；自动差异检查必须证明其余功能字段和源码路径一致。
记录真实运行率，重复相同矩阵，不能缩减为“启动一次试说一句话”。

若 48 kHz 配置在实际客户端下始终也运行 16 kHz，
报告必须说明两组主要比较的是初始配置差异，不能把结果解释成纯运行采样率因果结论。
若 16 kHz 对照失败而基线通过，恢复已验证基线，记录可复现条件；
不同时缩减采样率表、删隐藏设备或延长主程序超时来取得通过。

## 9. 分阶段交付与停止条件

| 阶段 | 必须完成 | 验证与提交条件 |
| --- | --- | --- |
| 一：冻结参考 | 校验来源，整理完整配置/构建差异清单，准备恢复材料和实验清单格式 | 每项差异有处置或待解决原因，提交追踪材料 |
| 二：建立基线 | 实验配置入口、对象恢复、完整率表、48 kHz 默认及构建对齐 | 配置边界测试、契约测试、两个架构构建和产物检查通过后提交 |
| 三：48 kHz 实测 | 授权安装、确认加载、MiRemoteV 对照、真实矩阵及长时间观察 | 保存结果与失败证据；通过才提交验收完成记录并进入阶段四 |
| 四：16 kHz 对照 | 仅默认值变化的配置、独立产物及同样验收 | 差异检查与实测完成后提交；失败则恢复基线并记录 |
| 五：结论 | 对照结果、保留差异、未测范围及正式发行建议 | 文档与产物清单对应，提交最终报告 |

PRD 获批后按阶段持续执行；每阶段对应验证后提交 Git，再继续已获授权且无外部依赖的工作。
提交格式使用 `type(scope): 中文描述`，PRD 路径写入提交正文。
需要用户真实按键测试、系统操作授权或无法确认加载状态时，明确说明具体依赖。
不能用自动化模拟或猜测补齐人工结果，也不能在缺少授权时修改系统音频配置。
故障未解决时提交诊断记录不代表该阶段验收通过。

## 10. 不在本轮范围

- 继续修改 TapSay 主程序的播放恢复、就绪状态或超时策略。
- 升级 BlackHole 上游、重构核心 IO、增添音效、自动优化运行采样率。
- 在 16 kHz 对照中同时缩减支持率表或隐藏对象。
- 改动 MiRemoteV 的安装、设备身份或源码。
- 自动替用户修改系统默认输出、重启服务或重启电脑。
- 公证、正式发布、扩大系统支持范围及声称未实测架构已稳定。

## 11. 预期结论与后续决策

1. 基线通过且 16 kHz 对照通过：保留两份证据，提出新的正式配置建议；
   用户确认后再更新发行合同。
2. 基线通过但 16 kHz 对照失败：保留基线，围绕唯一变化及实际率请求链继续定位。
3. 两者均失败或基线失败：优先核对实际加载版本、参考二进制来源、有效构建设置和保留差异，
   再提出有证据的下一轮实验，不自动恢复原来的多点修补路线。
4. 结果受权限、设备加载或人工测试缺失影响：明确标记未完成，不能写成验证通过。

### 12.2 Profile 数据与传递规则

1. profile 名称只能为 `reference-48k`、`reference-16k`。
2. 两份 profile 的下列字段必须逐项相等：默认值以外的采样率列表、
   声道数、主/第二设备输入输出能力、隐藏标记、Device transport、Box transport、
   latency、Device RingBufferSize、ring buffer 帧数、产品身份及构建宏。
3. `reference-48k.default_sample_rate_hz` 必须严格等于 `48000`；
   `reference-16k.default_sample_rate_hz` 必须严格等于 `16000`。
4. 上游率表必须严格按以下顺序保存，不得排序、去重、截断或把值转成范围：
   `[8000, 16000, 24000, 44100, 48000, 88200, 96000, 176400, 192000, 352800, 384000, 705600, 768000]`。
5. 每个入口脚本只解析一次 profile，并将解析后的规范化值传给子脚本；
   子脚本不得重新读取默认 profile。
6. profile 名称需进入构建目录、测试目录、报告文件名、实验包文件名和安装清单。
   即使两个实验使用同一版本号，也不得互相覆盖产物。
7. 报告内同时记录“请求 profile”“编译期默认率”“设备查询到的当前运行率”。
   这三个字段不可合并为一个 `sample_rate` 字段。
8. 未指定实验 profile 时，原正式构建入口应继续按既有发行行为运行，
   且不能把实验二进制打进正式包；实验入口则必须显式给出 profile。
9. profile 生成器要先写临时文件、通过完整校验后再原子替换输出；
   失败时不留下半份头文件或 plist。
10. 两个 profile 的实际生成配置做规范化比较。除 profile 名、默认率和实验报告元数据外，
    有任何差异都令检查失败并输出字段路径及旧值/新值。

### 12.3 对照上游的工作方法

1. 以固定 BlackHole 提交源码为唯一行为基准，不以搜索结果、记忆或当前安装驱动属性代替源码。
2. 对每项配置标注参考源文件/属性、参考值、当前值、目标值和差异原因。
3. 先比较差异，再改代码；禁止先批量替换 C 文件后再倒推改了什么。
4. 对象枚举至少逐个比较以下查询的“所需字节数、写入数量、对象顺序、UID 对应关系”：
   - 插件拥有对象、插件 DeviceList、插件 UID→Device 和 UID→Box。
   - Box 拥有对象、Box DeviceList、设备 UID 和 Box UID。
   - 主设备拥有对象、第二设备拥有对象、流列表与控制列表。
5. 每个查询都检查 buffer 容量为 0、1 个对象、准确数量及多于准确数量。
   返回字节数必须等于实际写入元素个数乘以元素大小；不能只断言查询成功。
6. 第二设备虽然隐藏，仍需按照上游被枚举和 UID 翻译的方式实现。
   不能仅把 `kDevice2_IsHidden` 设为 false，也不能只恢复 DeviceList 而遗漏 Box 列表。
7. 第二设备 UID 使用 TapSay 自有前缀，并单测与主设备、MiRemoteV 和上游 BlackHole UID 不相等。
8. 主设备仍为唯一显示名称 `TapSay Audio 2ch`；第二隐藏设备使用与参考命名格式等价、
   但带 TapSay 品牌的名称。不得把第二设备展示在 TapSay 引导页的声卡选项中。
9. Device transport 必须报告 USB；Box transport 必须报告 Virtual。
   测试必须分别查询两处属性，不能通过一处属性推断另一处。
10. 先修正确认的对象枚举/缓冲区缺陷，再补测试。禁止为了通过旧断言删除第二设备或缩减率表。
11. OwnedObjects 的第二项必须写在索引 1。返回项数为 0 或 1 时不得写越界；
    返回项数大于实际对象数时按实际数截断。
12. 不复制参考项目的产品 UUID、Bundle ID、用户品牌资源、安装器或签名身份。
    对比的对象是驱动行为和音频配置。

### 12.4 每阶段具体执行清单

**阶段一：冻结参考**

1. 核对 TapSay Audio 仓库起始提交与工作区；有用户未提交改动时保留并隔离。
2. 重新校验 BlackHole 固定提交/归档散列，以及参考脚本和补丁散列。
3. 将无线麦宏覆盖、补丁和 Release build settings 导出到阶段记录；逐项映射至本项目。
4. 补齐属性矩阵，特别确认第二设备在插件、Box、UID 翻译和拥有对象接口中的完整行为。
5. 写出两个 profile 的预期差异表，并运行差异检查设计的正向与反向用例。
6. 阶段通过条件：没有“未知但暂按相同处理”的配置项；保留差异均已写明理由。
   阶段报告提交后才进入阶段二。

**阶段二：建立 48 kHz 基线**

1. 增加 profile 数据结构和严格验证；先只生成配置，不安装、不触碰系统音频设置。
2. 实现第二设备与完整上游率表，并修正本 PRD 列明的 transport 差异。
3. 运行两个 profile 的元数据校验与配置差异校验。
4. 依次运行 `bash scripts/run-driver-contract-tests.sh reference-48k`、
   `bash scripts/run-driver-contract-tests.sh reference-16k`。
5. 依次运行 `bash scripts/build-driver.sh reference-48k`、
   `bash scripts/build-driver.sh reference-16k`；若接口采用环境变量，
   README 与阶段报告必须给出等价、可复制的确切命令。
6. 检查 arm64/x86_64 每个产物的身份、架构、部署下限、默认率、13 个支持率、
   Device USB、Box Virtual、隐藏设备及构建清单。
7. 两个 profile 的编译产物可以分别构建，但只有 48 kHz profile 进入下一步安装实测；
   16 kHz 此时只做自动构建，不提前安装。
8. 阶段通过条件：两 profile 自动测试与双架构构建通过；无产物混淆；
   随机选择任意一个 profile 查询清单均能还原完整构建配置。

**阶段三：48 kHz 实机验收**

1. 实机操作前输出待执行操作单：测试包完整路径及散列、覆盖目标、当前安装版本、
   备份路径、当前默认输入/输出/提示音设备和当前设备率。
2. 先用只读诊断工具保存系统路由快照；构建并验证实验 PKG。
   不运行会清理整个 `dist` 的正式打包脚本。
3. 用户授权安装后，使用既有事务安装机制覆盖 TapSay Audio；
   不卸载 MiRemoteV、不改变系统默认输出、不自动重启。
4. 按需要重新加载 HAL 时，先列明具体重启对象和可能影响，取得授权后操作。
5. 安装后同时核对磁盘文件散列、系统报告的 Bundle ID/版本/架构、
   设备 UID、实际设备动态 ID、支持率和当前运行率。任何一项不能确认即停止，
   标记“加载版本未确认”，不做 RC003 成败结论。
6. 按第 8.3 矩阵逐项记录。每轮在 MiRemoteV 和 TapSay Audio 间按相同顺序切换；
   失败后先保存日志、环境和系统状态，禁止连续重试后只记录成功的轮次。
7. 恢复前记录的默认输入/输出/提示音和采样率；验证恢复结果并写入报告。
8. 未达到样本数、60 分钟运行时长或任一关键状态未知时，结论只能是未完成。
9. 目标故障出现一次即将阶段标为失败/待分析，并暂停阶段四；不通过增加超时、
   清缓存、改变主程序代码或重装覆盖失败证据。

**阶段四：16 kHz 单变量对照**

1. 只有阶段三完整通过才可开始。
2. 使用 `reference-16k` 构建，自动检查两配置规范化差异只有默认率和明确标识。
3. 保存 reference-48k 通过产物、清单和安装回退材料。
4. 按阶段三同一主机、主程序、遥控器、工具、路由、操作顺序及矩阵重复测试。
5. 安装后必须实测真实运行率；若目标软件将设备切到其他采样率，报告该轮实际率，
   不能把它写为 16 kHz 运行结果。
6. reference-16k 任一关键音频测试失败时，停止该组，保存失败材料，
   并按既有事务机制恢复 reference-48k；恢复也需要用户授权。
7. 不得在此阶段改支持率列表、设备隐藏、transport、主程序或测试矩阵。

**阶段五：整理结论**

1. 报告列出每个 profile 的代码提交、清单散列、安装版本、实际运行率及逐格结果。
2. 明确区分自动回调测试、构建检查、系统设备检查、合成环回、
   RC003 实际音频和第三方文字输入。
3. 逐项列出通过、失败、未执行、权限阻塞和无法确认，不得用“基本正常”覆盖细节。
4. 只提出下一步建议，不自动把实验参数写成正式产品默认值。
5. 阶段报告和对应代码提交完成后，才能结束本 PRD。

### 12.5 必须实现的自动测试案例

以下案例是必须覆盖的外部可观察合同，不要求测试私有函数名称或代码布局：

- Profile：两个合法名接受；空名、拼写错误、大小写错误、第三个任意名拒绝。
- Profile：切换两配置时默认率恰好分别为 48000/16000；其余规范化配置完全相同。
- 率表：精确 13 个值、精确顺序；测试不得以集合比较掩盖错误顺序。
- 身份：主设备 UID、第二设备 UID、Box UID、Model UID、插件 UUID 各自稳定且互不冲突；
  两个 profile 之间身份完全相同。
- 设备列表：主设备及隐藏第二设备按参考语义返回；隐藏状态正确；
  TapSay UI 可见候选仍只有主设备 UID。
- Buffer：对象列表请求容量为 0、1、准确数量和过量时，实际写入与报告大小匹配。
- transport：主设备 USB，Box Virtual，二者分别查询。
- 采样率：两个 profile 各自初始率正确；列表中的每个率均被接受声明；
  不在列表中的代表性值被拒绝。
- 音频格式：每个采样率在输入与输出流都声明双声道 Float32 格式，
  `mSampleRateRange` 起止值等于离散采样率本身。
- OwnedObjects：零、一、两项请求分别返回正确内容，第二项为设备对象；
  未获取 Box 时不返回/写入无效 Box 对象。
- 产物隔离：先后构建两 profile 后，前一个产物散列不被后一个构建覆盖。
- 身份防泄漏：产物包含 TapSay 身份；不含 BlackHole/MiRemoteV 作为当前产品身份，
  但许可版权文本和来源说明必须仍在发行材料中。

若某案例无法通过当前 C 回调测试直接观察，添加最小的只读测试入口或静态产物检查；
不能因此删除该验收点。测试入口不得进入系统 HAL 发布二进制。

### 12.6 失败处理和禁止操作

- 某项参考配置在锁定提交源码中无法确认：阶段一失败，报告缺少的证据；不得凭另一分支推断。
- 配置生成、元数据验证或产物校验失败：立即停止，不构建、不安装、不将旧产物当作新产物。
- 自动测试失败：保存完整命令、退出码和日志；修复当前阶段后从该阶段验证入口重跑。
- 构建成功但静态报告写 `not_run` 的安装/音频项目：不得改写为通过。
- 安装事务失败或回退失败：停止后续测试，保留事务日志和备份，不自行删除系统文件。
- 不使用 `rm -rf` 清理系统驱动、用户备份、共享 `dist` 或非本实验构建目录。
- 不调用 `sudo`、系统设置变更、HAL 重启、默认设备切换或真实安装，除非用户已针对该操作授权。
- 不把新增隐藏设备作为用户可选声卡；不把当前主设备 UID 改成兼容无线麦 UID。
- 不把来源相同解释为实现必然相同；不把 48 kHz 默认值解释为运行时必然 48 kHz。
- 不把单次成功、模拟测试、构建通过或设备可见称为真实 RC003 端到端通过。
- 不新增与实验无关的格式化、重命名、安装器清理或主程序修复。
