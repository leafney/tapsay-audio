# 安装临时回滚与卸载残留清理补充 PRD

日期：2026-10-19

状态：产品方向已确认，本文实现规格待用户批准；本轮不实现、不删除系统文件。

关联原规格：[声卡发行 PRD](2026-10-18-audio-driver-distribution.md)。批准后，本文覆盖原规格中“安装成功后长期保存历史备份”和“普通卸载默认保留所有历史备份”的规则；失败恢复保护、范围核验及独立发行边界继续有效。

## 1. 问题与解决方向

用户已经验证修复版卸载正常执行。窗口仍列出历史 backup.driver，用户认为这些文件对普通用户价值有限，并希望从安装阶段减少残留。

用户已确认：

1. 新版不再创建长期保留的历史驱动备份。
2. 保留覆盖安装期间的临时旧驱动，用于安装失败时恢复。
3. 安装成功或失败后恢复成功，应自动清理本次临时材料。
4. 仅在失败且恢复未完成时保留必要材料，并明确提示。
5. 普通卸载自动清理可安全确认的旧版历史残留，不增加备份复选框或备份管理界面。

本方案仅属于 tapsay-audio。主程序正由另一会话开发，本会话不修改、提交或回退主程序的并行改动。

## 2. 用户故事

1. 作为普通用户，我希望安装成功后直接使用，不管理历史备份。
2. 作为覆盖安装的用户，我希望安装失败时原来的版本能自动恢复。
3. 作为重装或降级用户，我希望获得同样的临时恢复保护。
4. 作为卸载用户，我希望一次确认即可清理本产品和正常历史残留。
5. 作为已卸载用户，我希望再次运行新版工具就能清理旧版留下的备份，无需重新安装声卡。
6. 作为遇到异常的用户，我希望知道驱动移除和附加清理各自的结果。
7. 作为维护者，我希望异常中断和清理失败不会删除唯一恢复材料，也不会假报已清理。
8. 作为其他虚拟声卡用户，我希望相关驱动、配置和备份完全不受影响。

## 3. 现状与实施边界

现有事务同时保留两种旧版材料：覆盖前复制一份长期 backup.driver，部署时再将旧驱动移动到 HAL 下的临时 previous 路径。正常失败恢复实际使用 previous；成功时仅删除 previous，额外复制的备份留在历史事务目录。

卸载修复基线提交为 `cc8b6ee`：界面正确传递参数，结果严格解码，并检查目标设备 UID 是否消失。用户已实测正常卸载。此次必须保留这些修复，不能为了清理备份退回“执行命令即成功”的判断。

模块职责：

| 模块 | 修改范围 |
| --- | --- |
| 安装事务 | 取消长期复制，维护临时旧版与事务状态，提交或恢复后清理 |
| 历史材料识别与清理 | 核实本产品身份、记录阶段、受保护材料及允许的删除清单 |
| 卸载事务 | 在正确时机执行历史清理，并允许已卸载场景进入清理 |
| 卸载结果协议及界面 | 分别展示设备移除与历史清理状态 |
| 隔离测试及包检查 | 验证恢复、无残留、异常保护和实际包内工具 |
| README、包内说明和实施报告 | 删除正常保留历史备份的承诺，记录例外与实测 |

不新增常驻服务、历史版本恢复功能或独立清理程序。不修改设备身份、采样率、系统默认路由或主程序。本项目仍允许新版、同版及旧版覆盖安装。

## 4. 安装事务设计

### 4.1 临时材料和记录

1. 继续使用原子移动临时保留旧驱动，不额外复制一份长期 backup.driver。
2. 修改已有驱动前，持久化本次事务记录：记录版本、事务 ID、本产品身份、固定目标、是否有旧版、临时新旧路径、必要旧状态及当前阶段。
3. 所有记录路径先验证属于预期固定目录；记录里的任意字符串不能直接变成允许删除的路径。拒绝符号链接和身份不符的对象。
4. 事务记录按原子写入更新。相邻阶段可根据实际文件和记录判定，但不允许在证据不一致时推断旧驱动无用。
5. 安装、卸载和清理共用同一事务锁，不新增互相独立的锁；不得在持锁时调用会再次申请同一锁的公共入口。

### 4.2 阶段和结果

| 阶段 | 动作 | 异常时要求 |
| --- | --- | --- |
| prepared | 验证载荷、旧驱动与状态，落盘记录，准备临时新载荷 | 未移动旧版时，旧驱动及状态保持不变 |
| replacing | 将旧版移到临时位置，将新载荷移动到正式目标 | 根据真实移动结果恢复，不能仅依赖内存标记 |
| validating | 执行既有安装必要检查，写入新安装状态 | 检查或状态写入失败时恢复旧驱动及旧状态 |
| committed | 本次部署事务已提交，不再使用临时旧版回滚 | 清理失败不倒退为部署失败，不回滚已提交的新版本 |
| rolled_back | 本次失败已恢复旧版，或首装失败已清理本次新载荷 | 清理本次无用暂存及记录，不新增历史备份 |
| recovery_required | 部署失败且旧版/旧状态恢复未完成 | 保留仍有用的旧版和记录，报告精确路径，停止自动清理 |
| cleanup_pending | 部署已提交或恢复已完成，但临时材料删除失败 | 清楚报告残留；下次获锁操作可核实后重试清理 |

成功边界是当前安装事务的既有必要检查完成、状态写入并提交，不以第三方软件识别成功为提交条件。本补充不把启动音频服务的退出成功当作设备已就绪，也不新增“重启后仍可从临时文件自动恢复”的承诺。设备待核验、待重启、音频链路未验证等既有状态继续如实展示。

系统 Installer 收据由既有 PKG 流程管理，不直接改写系统收据文件来伪造恢复。报告区分驱动/安装状态恢复与系统收据结果，未核实的项目不能称为已全部还原。

### 4.3 清理规则

- committed 或 rolled_back 后删除本次已无用的临时旧版、暂存新载荷及事务材料；安装成功状态不指向已删除的备份，也不保留失效 backup 路径。
- 不能使用 `try?` 静默忽略清理失败。清理失败时保持已提交/已恢复结果，并记录 cleanup_pending、残留路径和原因。
- 后续重试清理前，重新核实事务终态、目标和所有者；只能清理该已完成事务自己的材料。
- 发现 recovery_required、未完成事务或证据矛盾时，禁止新安装覆盖其唯一恢复来源，提示待恢复后停止该事务。无需新建自动恢复后台服务。
- 进程异常结束后，后续入口先检查持久记录。不能因为进程不在或文件较旧就自动删除 previous。
- 首装不存在旧版时，不生成虚假的旧版备份；失败后只清理本次新载荷，保留失败原因。

这里的“没有备份残留”适用于正常完成及恢复成功且清理成功的流程；异常待恢复和清理失败是明确列出的例外，不隐瞒残留。

## 5. 旧版历史残留识别

新版不再新增长期备份；旧版已留下的材料由新版卸载入口清理，不在普通安装开始时无条件删除全部历史。

### 5.1 允许清理的证据

- 只从本产品固定 Application Support 下的事务目录枚举，不扫描整个系统找同名 backup.driver。
- 目录名和结构符合已发行版本的记录格式；驱动 Bundle ID、入口、工厂及二进制设备 UID 符合本产品；有旧状态时，其目标和身份也必须一致。
- 清理核验不要求旧备份版本等于新工具版本，也不因本产品历史备份属于另一受支持架构而错误认定为其他产品。与安装载荷校验分开，不能直接套用“必须为当前包版本和主机架构”的条件。
- 仅删除经核实的文件和已空的专属目录；目录含未识别对象时保留并报告，不能递归删除整棵目录。
- 不能删除锁文件以“清干净”：锁持有期间 unlink 会让另一个进程创建新锁并发进入。锁文件可保留，且不作为历史备份残留；不用这个小文件创建清理选项。

### 5.2 必须保护的材料

活动事务、待恢复事务、无足够归属证据、符号链接、记录路径越界、产品身份不符、无法读取或清理权限失败均不得盲删。

旧版记录缺少阶段信息时，不能仅凭名称或时间判断安全。仅当正式驱动、安装状态、收据均已清理、设备 UID 确认消失，且没有本产品异常 previous 或其他待恢复证据时，才允许按上述身份和结构核验清理旧历史。仍无法分类的材料保留并说明，不要求用户猜测如何手动删除。

## 6. 卸载流程与界面

1. 确认页说明将清理驱动、收据、专属安装状态及可安全移除的历史安装材料，不再显示“恢复备份会保留”。
2. 用户确认和授权后加锁，验证现状；正常卸载仍按现有规则清理驱动、收据、状态。
3. 继续实际枚举目标 UID，沿用设备移除、待重启、无法确认的判断，不能跳过。
4. 只有确认设备已消失，且不存在受保护恢复材料，才执行相应历史清理；逐个核验和记录结果。
5. 文件已清理但设备仍在或无法枚举时，保留相关恢复材料，说明“历史材料清理待卸载生效后执行”，提示重启或复查。
6. 已经卸载的用户再次打开新版工具，同样经过确认、授权和锁；确认不存在设备后清理可核实历史。禁止原有“没有驱动和收据即提前返回”的路径漏掉历史。
7. 没有任何驱动、收据、状态和历史材料时报告未安装；重复操作不出错、不扩大范围。
8. 历史清理失败不撤销已经完成的卸载，也不自动重装驱动；显示“声卡已卸载，部分历史材料未清理”，附原因和路径。

不增加复选框、备份列表页或强制用户手动定位目录。

## 7. 结果协议和文案

扩展现有结构化卸载结果，明确设备结果与附加清理结果；界面和事务工具一起升级并打包，旧或不完整响应不能被猜测为成功。

清理结果至少区分 notNeeded、complete、partial、blocked、pendingDeviceRemoval，包含本轮删除数量、残留数量、路径及原因。保留现有本产品 UID 和驱动/收据/状态不存在的核验字段。

| 实际情况 | 展示 |
| --- | --- |
| 设备已消失，无历史或清理全部成功 | 卸载完成 |
| 已无设备，旧版历史已清理 | 历史安装材料已清理，当前未安装 |
| 设备仍待重启 | 卸载待重启生效，历史材料清理尚未完成 |
| 设备状态无法确认 | 卸载生效状态待确认，不宣称全部清理 |
| 设备已消失，部分历史无法删除 | 声卡已卸载，部分历史材料未清理 |
| 检测到待恢复材料 | 明确说明保护原因；不显示“已全部清理” |
| 驱动、状态或收据本身清理失败 | 卸载未完成，按现有失败结果处理 |

不得将成功卸载的历史备份统一提示为应永久保留，也不得隐藏失败恢复材料路径。

## 8. 测试与验收

不采用 TDD。重点测试事务状态、异常恢复和清理范围；复用原生事务隔离根目录及现有卸载协议测试，不在普通自动测试中修改真实 HAL。

| 场景 | 必须验证的外部结果 |
| --- | --- |
| 首装、升级、同版重装、降级成功 | 新驱动和状态正确，本次无长期 backup、previous、staged 或无用事务目录 |
| 修改前失败 | 原驱动和状态字节不变，无新增无用副本 |
| 部署后失败 | 旧驱动和状态恢复，已无用临时材料清理，失败结果准确 |
| 首装失败 | 仅移除本次新载荷，不新增旧版备份或伤及其他对象 |
| 自动恢复失败 | 唯一可用旧版和记录保留，后续操作不将其清掉或覆盖 |
| 各关键阶段异常中断 | 持久记录与真实文件可判定；证据不足时停止，不误清理 |
| 已提交后清理失败 | 新版保持已提交，记录 cleanup_pending；重试只清理当前事务材料 |
| 正常旧版历史 | 新版卸载确认设备消失后自动清理，无复选框 |
| 已卸载且只剩历史 | 无需重装声卡，即可通过新版卸载工具清理 |
| 待重启或无法枚举 | 不提前删除受保护材料，不显示全部清理成功 |
| 外来文件、链接、越界状态、非本产品备份 | 原对象及内容不变，说明被跳过原因 |
| 混合正常与异常历史 | 仅清理确定安全的项；结果区分完整和部分清理 |
| 并发安装、卸载、清理 | 仅一个事务修改，锁文件保留，不出现第二把有效锁 |
| 授权取消和缺少确认 | 无删除和其他副作用 |
| 结果缺失或协议不一致 | 界面拒绝宣称成功 |
| 重复卸载/清理 | 稳定报告现状，不误报残留已清理或扩大范围 |

测试必须比较实际文件内容与目录清单，不只断言退出码。异常终止测试使用子进程和隔离目录；设备枚举状态在隔离测试中注入，标明是模拟，不能写成实机设备已消失。

两个架构均编译并验证包内工具、配置、说明和源码材料一致。arm64 包内实际事务程序执行隔离安装卸载；Intel 未有真机，不能将编译结果写成 Intel 真机通过。

真实历史清理需由用户主动运行新版工具，或另获具体系统修改授权。本次 PRD 批准不等于允许代理立即删除本机现有约 84 KB 材料。实测由代理核对前后清单、归属、设备 UID 与收据，用户不需要凭感觉判断。

本文批准后才修订原规格的生效规则并开始代码。每阶段运行对应验证，在当前仓库按 Conventional Commits 提交，描述简体中文，正文引用本文；提交后继续下一阶段，不逐文件重复确认。遇到关键决定、权限或真实操作依赖时明确说明，能独立完成的工作继续推进。

完成标准：不再新增长期历史备份，正常安装及恢复成功后的本次临时材料已清理；正常历史能由新版卸载清理，异常材料不误删；清理失败不假报成功；代码、测试、文档及包内实际行为一致。真实系统清理未完成时，编码交付与实机验收分别报告。
