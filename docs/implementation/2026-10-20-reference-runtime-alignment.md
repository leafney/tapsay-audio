### 原因分析及证据边界

新驱动与固定主程序没有在这次对齐中修改。主要操作是正常退出并重开应用，
以及把 TapSay 的实际运行率从 16000 Hz 设为 48000 Hz。
此前 20:25:43 重开应用后仍在 16 kHz 的切回场景复现，因此“仅重启应用”
不足以解释已有全部记录；实际运行格式差异是目前最有力的调查方向。

当前合理推断是：遗留的 16 kHz 设备运行状态与切换、音频图重建路径的组合
触发了播放探测停滞，对齐 48 kHz 后本批未再触发。
该推断不等于已经定位引擎或 HAL 的具体故障行；本次同时包含应用重启，
没有执行再次切回 16 kHz 的交叉实验，不能宣称严格的单变量因果证明。
此前 16 kHz 也有成功样本，参考驱动本身支持该率，所以不能得出
“所有 16 kHz 都不能工作”或“两张卡使用不同率必定错误”的结论。

遥控器解码后的客户端输入保持 16 kHz 单声道；两张卡的成功记录都如此。
该源格式与设备 48 kHz 输出共存正常，不应为了让数字相同而修改遥控器解码率。
